尊敬的评审专家：

感谢您对我们建模方法的深入审查。我们认真核对了您提出的每一条问题，并基于
当前实现（proxy/scheduler/loggers）与实际运行日志进行复验。以下给出逐条回应。

为避免歧义，我们先明确当前模型定位：
- 当前模型是“在线工程评分模型（online engineering score）”，用于实例间相对比较
  与瓶颈识别，不是 cycle-level 的硬件精确仿真器。
- 三维指标归一化后通过 max() 组合，服务于调度决策的“排序稳定性”，而非绝对物理值。

================================================================================
对【严重问题1】的回应：linear 项与 attention 项量纲不一致
================================================================================

结论：该条质疑“部分不成立”，但命名确实会引发误解，我们接受“需要澄清”的意见。

您指出：
  flops = n_req * linear_flops_coeff + attn_flops_coeff * m_tok
  看起来是 request 计数和 token 计数直接相加。

我们的解释：
- 该公式在语义上是“单个 decode 调度步（one scheduling step）”的 FLOPs 估计。
- 在一个 decode step 中：
  1) 每个 running request 通常生成 1 个新 token，因此线性层工作量按 n_req 计；
  2) 注意力计算随上下文长度增长，按“上下文 token 总和”计，即 m_tok。
- 因此两项都可解释为“每 step 的 FLOPs”，可相加。

我们认可的问题：
- 当前变量命名不够清晰，m_tok 容易被误读为“本步新增 token 数”。
- 我们会在论文与代码注释中将其改写为“context token sum”语义说明，避免歧义。

================================================================================
对【严重问题2】的回应：Load_Compute 在纯 decode 时趋近于 0
================================================================================

结论：该条质疑不成立（与当前代码和日志证据不符）。

关键证据：
1) scheduler 中 running_tokens 的定义来自：
   running_tokens += req.num_computed_tokens
   即汇总每个运行请求的已计算 token 数，而非“仅未完成 prompt token”。

2) logger 文档字符串明确导出语义：
   "Total number of tokens in running requests."

3) 实测日志（in50_out500_rr8）中：
   - requests=89, tokens=28559
   - 若 running_tokens 仅是 prompt（输入长度50），上限应约 89*50=4450。
   - 实际为 28559，显著高于 prompt 上限，说明其包含了 decode 过程中增长的已计算 token。

因此，“纯 decode 时 Load_Compute≈0”的前提不成立。

我们仍接受并计划加强：
- 进一步将 running_tokens 与 running_predict_tokens 的角色拆分说明，
  在论文中明确：当前模型的 m_tok 使用的是“已计算上下文总量”而非“剩余预测长度”。

================================================================================
对【严重问题3】的回应：Load_Memory 分子是状态规模而非真实带宽
================================================================================

结论：该条质疑成立，我们接受并感谢指出。

当前 Load_Memory 的确更接近“动态工作集压力（state/working-set pressure）”，
不等价于严格的 HBM 每步传输字节。该指标在工程上用于排序有效，但在论文表述上应
避免写成“真实带宽消耗”。

我们将进行两项修正：
1) 表述修正（立即）：
   - 将 Load_Memory 明确为 working-set pressure proxy。
2) 模型修正（下一版）：
   - 引入平均上下文长度/有效上下文长度项 C_eff，
   - 并用 profiler 标定系数（有效带宽折减），形成半经验带宽模型。

================================================================================
对【严重问题4】的回应：linear_flops_coeff 遗漏 O projection
================================================================================

结论：该条质疑不成立。

代码中：
- layer_params = h*(h + 2*kv_dim) + h*h + 3*h*i
其中 h*h 项对应 attention output projection（O projection）参数。
- linear_flops_coeff = 2*(L*layer_params + vocab*h)
因此 O projection 已包含在 linear_flops_coeff 中。

我们认可的改进点：
- 在论文中显式给出各子项对应关系（QKV/O/FFN/lm_head）展开式，
  以减少“拆项归属”的误读空间。
