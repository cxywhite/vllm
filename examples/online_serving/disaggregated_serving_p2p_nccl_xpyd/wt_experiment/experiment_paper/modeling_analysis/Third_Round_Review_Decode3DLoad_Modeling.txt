一、对 4 个未决事项的最终评估
================================================================================

【事项A：pure decode 适用边界】

工程师给出的拟新增表述：
  "本文负载模型针对 disaggregated decode 实例，默认 running 队列中的请求均处于
   decode 过程。若存在 prefill/decode 混合批，attention 上下文统计会引入附加误差，
   该场景不在本文模型主要适用范围内。"

评估：**接受。该表述清晰、准确地在论文中划定了模型的适用边界，
         与二审期望一致。运行时 warning 机制是额外的工程保障。**

【事项B：off-by-1 计数说明】

工程师的定量推导：
  M_end - M_start = R → 相对偏差 ≈ 1 / C̄（C̄ 为平均上下文长度）

并给出代码级修正：
  M_eff = max(running_tokens - running_requests, 0)

评估：**接受，且修正方案具有技术优雅性。**

  补充说明（可写入附录）：该修正在数学上恰好等于"step 开始时的上下文总量"，
  因为：
    M_start = Σ(C_i) = Σ(C_i + 1) - R = M_end - R
  即用当前 running_tokens 减去本步新增 R 个 token，得到上一步结束时的上下文量，
  从而消除了 off-by-R 的系统性高估。

  在长输出稳态（C̄ ≥ 100）下原始误差 < 1%，修正后误差进一步压缩至 < 0.1%，
  属于锦上添花性质，但修正思路正确。建议保留该配置项作为可选功能。

【事项C：Load_Memory 重命名与双指标框架】

工程师引入的双框架：
  - Load_Memory_WS（当前版本）：working-set pressure proxy，状态规模压力
  - Load_Memory_BW（下一版本）：带宽压力，引入 C_eff 和有效带宽系数

评估：**接受，且分层策略合理。**

  论文写作建议：v1 版本的 Load_Memory_WS 命名已足够清晰，但请确保在同一段落
  中明确说明：
    (a) WS 指标是"动态状态相对容量"的近似，与真实 DRAM 带宽消耗无固定比例；
    (b) WS 和 BW 两项服务于不同粒度的调度决策（容量调度 vs 带宽瓶颈归因）。

【事项D：Nsight ground-truth 验证协议】

工程师给出的协议包含：
  - 3 个场景 × 5 个并发点
  - Nsight Systems（并发行为）+ Nsight Compute（Tensor Core / DRAM）
  - MAPE + Pearson/Spearman + Top-1 瓶颈判定准确率

评估：**接受，协议设计完整且可操作。**

  补充建议：
  1) 在散点图之外，建议额外报告"分位数误差"（P50/P90/P99），以覆盖长尾调度
     场景下模型失效的尾部风险；
  2) 明确采集的 GPU kernel 粒度（Attention kernel / Linear kernel / All kernels），
     以便审稿人理解对照数据的具体物理含义；
  3) 若实验条件受限，应在论文 limitations 中诚实说明，并给出理论误差上界
    （如 off-by-1 误差 1/C̄ 的最坏值）。
