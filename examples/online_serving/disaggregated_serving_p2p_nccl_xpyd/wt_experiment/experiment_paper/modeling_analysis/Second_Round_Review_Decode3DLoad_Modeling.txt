【关于问题1】linear 项与 attention 项量纲不一致
================================================================================

工程师回应：部分接受——解释成立，但命名须澄清。

本轮核查结论：**工程师解释成立，维持接受态度。**

详细说明：
  经对 pastfuture_scheduler.py:128-130 的深入核查：
    num_new_tokens = (request.num_tokens_with_spec
                      + request.num_output_placeholders
                      - request.num_computed_tokens)

  关键语义确认：
  - num_computed_tokens 在 decode 阶段等于"已处理 token 总数"（prompt + generated）。
  - running_tokens = Σ(num_computed_tokens) = Σ(每个请求的上下文长度)。
  - 在一个 decode step 中：
      * linear 层处理"本步新增的 n_req 个 token"，FLOPs = n_req * per_token_linear_flops ✓
      * attention 层：每个新 token 的 Q 参与 K^T 矩阵乘法时，K/V 的长度
        等于该请求的当前上下文长度，即 num_computed_tokens。
        因此 attention FLOPs = Σ(context_length_i) * per_token_attn_flops = running_tokens * coeff ✓

  两项均以"每 step FLOPs"为基准，可直接相加。

  残留关注点（不推翻结论，但须在论文中说明）：
  - 在混合批（prefill + decode 共存）场景下，attention 项的 m_tok 同时覆盖了
    prefill 片段和 decode 片段的上下文长度，会导致 attention 压力被重复计入。
  - 但在 disaggregated decode 实例中，运行请求全部处于纯 decode 阶段，
    不存在该问题。此假设须在论文中明确标注。

  建议论文表述：
    "本模型针对 disaggregated decode 实例设计，假设所有 running 请求均处于
     decode 阶段。对于混合批场景，该近似会引入误差。"

【关于问题2】Load_Compute 在纯 decode 时趋近于 0
================================================================================

工程师回应：该质疑不成立，日志证据（requests=89, tokens=28559）证明
running_tokens 包含 decode 增长。

本轮核查结论：**工程师立场正确，初始质疑须撤回。**

详细说明：
  async_scheduler.py:23-27 明确揭示了 vLLM v1 的计数机制：
    当 request.num_computed_tokens == request.num_tokens + num_output_placeholders
    （即 prefill 完成）时，num_output_placeholders 递增；
    在 _update_request_with_output 中，num_computed_tokens 被更新为
    "本次 forward 处理的实际 token 数"。

  这意味着：
  - decode 实例中所有 running 请求的 num_computed_tokens 均代表
    "prompt + 已生成 token" 的完整上下文长度；
  - running_tokens ≈ n_req * C̄（C̄ 为平均上下文长度），对于长输出场景
    此值远大于 prompt 上限，与日志数据完全吻合；
  - 因而 Load_Compute 在 decode 阶段的非零性是有理论和实验双重支撑的。

  初始质疑"纯 decode 时 Load_Compute ≈ 0"基于对 running_tokens 语义
  的错误假设（误认为其仅统计未完成 prompt tokens），此处予以正式撤回。

  新增残留问题（minor）：
  - attention FLOPs 使用 step 结束后的 running_tokens 而非 step 开始时的值，
    存在 off-by-1 的系统性高估；但在长输出稳态下该误差 < 1/C̄，可忽略。
  - 建议在论文 Appendix 中注明此 off-by-1 特性及其量级。

【关于问题4】linear_flops_coeff 遗漏 O projection
================================================================================

工程师回应：该质疑不成立，O projection 已包含在 layer_params 的 h*h 项中。

本轮核查结论：**初始质疑有误，工程师正确，须撤回。**

详细说明：
  经逐项展开公式（Llama 架构，Fused QKV 实现）：
    h*(h+2*kv_dim) 覆盖 QKV projection 参数（单个大矩阵）: 2*h*(h+2*kv_dim) FLOPs
    h*h 覆盖 O projection 参数: 2*h*h FLOPs
    合计 attention 部分 per-token FLOPs = 2*h² + 6*h*kv_dim

  其中：
    attn_flops_coeff * m_tok = 4*L*h * m_tok = 2*L*2*h*m_tok
    即对应 QK^T 和 softmax*P*V 的 4*h*m_tok（每层），O 投影已归入 linear 项。

  另外，FFN 部分（3*h*i 参数 → 6*h*i FLOPs per token）与 SwiGLU 的实际
  运算结构（gate+up+down 各一次矩阵乘）一致，layer_params 定义正确。

  初始质疑误判了 O projection 和 FFN 的归属，特此撤回。

二审综合结论
================================================================================

本次 rebuttal 交流后，初始 8 个问题中有 2 个须正式撤回（问题 2 和问题 4），
1 个部分成立（问题 1 的残留 prefill 干扰点），其余 5 个均被接受。

撤回理由汇总：
  - 问题2撤回：pastfuture_scheduler 代码证明 running_tokens 在 decode 阶段
    确实包含已生成 token 数，初始"纯 decode 时 compute≈0"的论断基于对指标
    语义的误解。
  - 问题4撤回：经逐项展开 Fused QKV 和 SwiGLU FFN 的 FLOPs，layer_params
    的参数计数（3*h*i 用于 FFN，h*h 用于 O projection）与 Llama 架构一致。

仍须在论文中明确处理的未决事项：

  1.【必须】明确模型适用场景为 pure decode batch，注明在混合批下的近似误差。
  2.【必须】完成 Nsight profiler 对照实验（问题7），这是目前论文说服力的
     最大短板；若无法在当前版本完成，须在论文 limitations 一节明确说明。
  3.【建议】补充 off-by-1 attention 计数说明（Issue 2 撤回时发现的新残留点，
     量级微小但须有文字记录）。
  4.【建议】将 Load_Memory 正式重命名，并在公式符号说明中区分
     "状态规模指标"与"带宽消耗指标"。

修改后的模型在理论上自洽性良好（问题1/2/4 均已澄清），工程师的代码-公式-日志
自洽性检查工作扎实。如能补齐问题7的 profiler 验证，该工作可以作为
"disaggregated decode 在线负载估计"的工程实践案例发表。
