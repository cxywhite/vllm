==================================================
一、先给结论（与你的问题对齐）
==================================================
在原生 P2P NCCL + PUT_ASYNC 逻辑中:
1) prefill 在每层 attention 计算后触发 save_kv_layer，按 request 和 layer 切片当前层 KV。
2) send_tensor 在 PUT_ASYNC 下只是入发送队列，后台线程异步出队并真正发送。
3) decode 侧通过 start_load_kv 对 request 的每层逐个 recv_tensor 并注入到对应 layer 的 kv_cache。
4) 由于发送是异步线程执行，prefill 可继续跑后续层前向，与网络传输并行。

三、按你提出的“完整过程”做一句话对照
==================================================
你要求的链路:
- prefill scheduler 调度 -> 展平为 [num_tokens, hidden_dim] -> 每层 attention/mlp 前向 -> 每层 attention 后保存 kv cache -> 异步发送线程并行发送 -> decode 侧接收每层 kv -> decode scheduler 调度 -> 每层 attention/mlp 前向 -> 生成增量 token 并更新本地 KV -> 输出完整结果。

与源码一致，并且关键并行点是:
- prefill 计算线程与 send_async 发送线程并行（PUT_ASYNC）。

==================================================
四、关键实现细节与易误解点
==================================================
1) decode 的 wait_for_layer_load 在 p2p connector 里当前是空实现（:208）。
   真实加载主要发生在 start_load_kv 的层循环（:182, :186, :198, :205）。

2) baseline 版 recv_tensor 在 PUT/PUT_ASYNC 分支读的是 recv_store[tensor_id]，
   默认不立刻 pop（p2p_nccl_engine.py:265 之后逻辑）。
   生命周期清理主要在 get_finished（:468 之后）做。

3) 当接收缓存超过阈值时会进 TensorMemoryPool（store/load）:
   - store: p2p_nccl_engine.py:349
   - load: p2p_nccl_engine.py:272
   对应 pool 实现在:
   /root/predict-schedule/baseline_experiment/vllm/vllm/distributed/kv_transfer/kv_connector/v1/p2p/tensor_memory_pool.py

4) decode 侧一般不是 producer，save_kv_layer 入口会直接 return（:234-235）。
   因此 decode 的“增量 KV 保存”是本地 attention KV cache 更新，不是再走一次远端发送。

            -> save_kv_layer

    -> scheduler.update_from_output
    -> 请求结束后 _free_request
