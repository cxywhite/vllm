# 第4章 Motivation
## 研究背景
### PD 分离架构下的调度挑战
现代大型语言模型（LLM）服务系统普遍采用 Prefill-Decode（PD）分离架构，将推理过程解耦为独立的 Prefill 阶段与 Decode 阶段，从而实现 TTFT 与 TPOT 的独立优化，并为两类阶段配置差异化的计算资源。
然而，分离架构在提升灵活性的同时也引入了两个新的系统级调度问题：（1）跨实例的 Prefill-to-Decode（P2D）路由，当请求完成 Prefill 后应被路由至哪个 Decode 实例；（2）Decode 实例内部的请求调度，请求到达 Decode 实例后应在何时、以多大并发度被调入 running batch。这两个问题共同决定了系统的端到端 Goodput。
现有方法在这两个层面均倾向于采用局部、单指标、短视的调度策略，仅利用当前可观测状态做决策，而缺乏对请求未来输出长度的有效认知。结果是：跨实例层面出现多维负载失衡，实例内层面出现 Preemption 与资源闲置并存，两者共同拉低系统 Goodput。
### 调度问题的统一根因
上述两个调度问题的表象不同，但共享同一个根因：现有方法缺乏对请求未来输出长度的可靠认知。具体而言：
对 waiting 请求，系统仅可观测 prompt 长度，无法直接获得最终输出 token 数。
对 running 请求，系统虽可观测当前已生成长度，但无法确定剩余生成时长。
跨实例路由通常仅感知当前负载，难以感知请求落地后的未来瓶颈；实例内调度通常仅做即时可行性判断，难以评估准入后的抢占传播风险。
因此，未来输出长度不是附加优化项，而是统一两阶段调度的关键信号。进一步地，跨实例路由与实例内调度结果共同表明，仅依赖单值预测难以充分表征长尾风险。对于 P2D 路由，请求落地后的负载压力取决于其未来输出长度；对于实例内调度，请求是否触发抢占取决于其输出长度是否超过可用显存阈值。因此，能够刻画不确定性的长度分布信息更适合作为两阶段协同调度的输入。
## 跨实例调度：为什么需要多维瓶颈感知
### 单一统计量无法刻画未来瓶颈
P2D 路由决策真正关心的，不是实例当前 queue 长不长、batch 大不大，而是新请求进入后会不会让该实例更快触碰其主导瓶颈，并最终拉低 Goodput。
只看单一统计量会系统性失真。例如：
仅使用 queue length 或 batchsize 会忽略长上下文带来的 KV 压力。
仅使用 batch tokens 会将少量长请求与大量短请求混为同类负载。
仅使用显存容量占用无法区分性能下降来源于容量逼近上限还是并发竞争。
前缀匹配调度依赖显式前缀复用，在无共同前缀或前缀差异较大场景下收益受限，并且难以感知输出生成引起的动态显存压力。
换言之，P2D 路由需要的不是抽象的忙闲分数，而是可解释的瓶颈状态表示。该状态表示应能够回答实例当前受限资源类型及后续演化方向，从而使路由器由当前负载感知转向未来风险估计。
### 三维负载度量
对 Decode 阶段而言，单步推理的主要资源约束对应三种不同的物理预算：计算预算、显存带宽预算和总显存容量预算。三者分别回答三个不同问题：
当前并发请求数是否已将计算推近 TPOT 边界。
当前运行 token 工作集是否已耗尽带宽预算。
当前模型权重、中间激活与 KV Cache 的总占用是否已逼近设备显存上限。
这三种压力的驱动因素并不相同。具体而言：并发请求数 n_req 更直接推高计算压力；运行 token 总量 m_tok 更直接推高 Attention 相关访存与带宽压力；而容量压力由模型权重、中间激活和 KV Cache 三者共同决定，三者随请求的上下文增长和生成推进而动态变化。
基于以上分析，本文采用三维负载度量 L_C、L_M、L_K 近似描述 Decode 实例的在线瓶颈状态：
计算压力定义如下：
L_C = F_decode / F_TPOT    (2-1)
其中，L_C 为计算压力指标；F_decode 为 Decode 单步理论 FLOPs；F_TPOT 为 TPOT 时间预算内可执行 FLOPs。
带宽压力定义如下：
L_M = (M_kv + M_act + M_weights) / M_TPOT    (2-2)
其中，L_M 为带宽压力指标；M_kv 为 KV Cache 访存量；M_act 为中间激活访存量；M_weights 为模型权重访存量；M_TPOT 为 TPOT 时间预算内可访问显存带宽。
容量压力定义如下：
L_K = (C_weights + C_act + C_kv) / C_total    (2-3)
其中，L_K 为容量压力指标；C_weights 为模型权重显存占用；C_act 为中间激活显存占用；C_kv 为 KV Cache 显存占用；C_total 为设备总显存容量。
L_bottle = max(L_C, L_M, L_K)    (2-4)

### 瓶颈动态切换特性
即使在单个 Decode 实例上，主导瓶颈也会随请求到达与完成在 compute、memory 和 capacity 之间切换。实验结果如图2-1所示：batch 增大初期 compute 和memory压力先升，memory增长超过compute；随着 KV 持续累积并带动总显存占用上升，capacity 逐步抬升并超过memory成为主导瓶颈；当部分请求完成后容量压力短暂回落，此时memory变为主导瓶颈；随后瓶颈在memory与capacity之间交替。

不同工作负载配置对应不同的主导瓶颈维度，如图2-2所示。短输入、短输出且高 QPS 场景中，并发请求数 n_req 较高而 KV Cache 较小，实例更偏向 compute 主导；长输入、长输出场景下，KV Cache 与中间激活访存量更大，当 TPOT 较低时每步可用时间更少，实例更偏向 memory 主导；当 TPOT 较高时访存压力缓解，但长输出会拉长 running 停留时间并持续累积 KV Cache，实例又转向 capacity 主导。

## 实例内调度：为什么固定策略不够
### 实例内调度的核心矛盾
Decode 实例内调度的核心问题，不是单步 decode 能否执行，而是在 waiting 队列存在时，系统应以多大的并发度接纳新请求进入 running batch。
Decode 阶段中，每个 running 请求都会持续累积 KV Cache，并随着生成推进逐步增加总显存占用与带宽压力。调入更多请求可以提升并行度、改善设备利用率；但并发度过高时，请求间会争夺资源，甚至触发 Preemption 与抢占传播。
因此，实例内调度面对的是一个典型平衡问题：过保守会造成资源闲置，过激进会造成干扰加剧和抢占恶化。调度的关键决策不是当前能不能执行一步 decode，而是现在是否应让一个 waiting 请求进入 running batch。
### 激进与保守的两难困境
在 1P1D 拓扑下，固定每个请求的上下文长度，并以最大速率发送不同 batchsize 的请求，观察 Goodput 随 batchsize 的变化。由于单请求长度固定，batchsize 增大时实例同一时刻承受的总负载也同步上升。结果如图3-1所示：Goodput 在小 batchsize 区间随并发提升而上升，但超过峰值后开始下降，呈现稳定的倒 U 型曲线。
这一结果表明，实例内调度存在最优并发区间。低于该区间时，GPU 计算与带宽利用不足；高于该区间时，请求间干扰、调度开销与 Preemption 风险显著上升，最终拖累 Goodput。
 
【图3-1 固定单请求长度下 Goodput 与 batchsize 关系】
进一步地，为区分“总负载”与“请求粒度”的作用，实验固定同一时刻实例内总 token 数（batch_tokens=160000），只改变 batchsize。此时 batchsize 越大，单请求 seq_len 越短；如果 Decode 性能仅由总 token 数决定，则 Goodput 应接近不变。但如图3-2所示，Goodput 仍先升后降，说明 batch_tokens 并非决定 Decode 性能的充分统计量，请求粒度本身会改变实例运行状态。
 
 
 
【图3-2 固定 batch_tokens 下 Goodput 与 batchsize 关系】
在 batch_tokens 相同条件下，进一步比较不同 input/output 长度构成：(40k, 120k)、(80k, 80k)、(120k, 40k)。结果同样如图3-2所示：output 占比越大，峰值 batchsize 越小；input 占比越大，实例可承受最优并发度越高。这说明在总 token 负载相同的前提下，长度结构会显著改变未来调度风险。
结论：实例内调度不能只看当前有多少 token，还必须同时考虑这些 token 由多少请求构成以及input/output 如何构成。长度总量相同不代表未来代价相同，真正影响调度稳定性的，是 token 在未来是否继续增长及其增长持续时间。
### 长度信息对实例内调度的指导作用
如果实例内调度能够获知每个请求的未来输出长度，并据此动态决定 waiting 请求的调入时机与并发度，其 Goodput 将显著优于固定激进或固定保守策略。实验在 1P1D 拓扑下对比三种策略：固定激进（始终最大 batchsize 准入）、固定保守（始终单请求运行）与 Oracle 调度（已知真实输出长度）。结果如图3-1所示，Oracle 调度的 Goodput 更高且 Preemption 频率显著更低。
结论：只要能够准确获知请求未来的输出长度，实例内调度就能够更合理地平衡资源利用率与 Preemption 风险。

## 核心挑战与思路
### 三大核心挑战
综合以上分析，本文方法面临以下核心挑战：
挑战一：如何在低系统开销下获得足够有用的分布信息。预测器过重会抵消调度收益，过轻则无法支撑两阶段决策。需要的是一种既能部署在真实 serving 路径上，又能输出足以支撑风险感知调度的长度分布的 Practical Prediction。
挑战二：如何设计高效的两阶段协同调度策略。在获得准确的长度分布预测后，跨实例层面需要根据三维负载与预测分布估计未来瓶颈，实例内层面需要根据长度风险动态控制准入节奏，两阶段共享一致的负载刻画与风险认知，实现真正的协同调度。
挑战三：如何在预测误差存在的情况下保证调度策略的鲁棒性。预测不足会低估长尾请求风险，导致错误路由或过早调入；预测过保守则会过度回避，造成资源闲置。因此，两阶段调度策略必须能够在预测偏差存在时仍保持鲁棒，跨实例层面，即使路由因预测误差将请求分配到非最优实例，实例内调度仍应能通过动态调整准入策略缓解局部过载；实例内层面，即使准入判断因长度预测偏差而失误，也应能通过 Preemptive 机制或重调度将损失控制在可接受范围内。
### 整体设计思路
基于以上分析，本文提出一个由输出长度分布预测驱动的两阶段协同调度框架：
跨实例层面：基于 Decode 实例的三维负载状态、running/waiting 队列信息和预测输出长度分布，估计请求落地后的未来瓶颈，做出更稳健的 P2D 路由决策。
实例内层面：结合请求状态、显存利用率与预测长度风险，动态平衡 waiting 请求的调入节奏，避免激进调度和保守调度两个极端。
两个层面共享对 Decode 未来瓶颈的建模，共同提升系统在长输出、高方差与突发负载下的端到端 Goodput。
