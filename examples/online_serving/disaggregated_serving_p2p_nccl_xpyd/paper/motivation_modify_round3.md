# Motivation 大纲（总-分-总结构，修订版 round3）

---

## 首段（总）

### §0 Motivation 总起

**首句**：PD 分离架构在解耦 prefill 与 decode 资源的同时，引入了两个新的系统级调度问题：跨实例的 prefill-to-decode 路由与 decode 实例内部的请求调度，而两者共同决定系统端到端 goodput。

**本段内容**：
- PD 分离的价值在于分别优化 TTFT 与 TPOT，并为 prefill 与 decode 配置不同资源。
- 但分离也把原本局部的执行问题转化为两个新的调度问题：请求 prefill 完成后应被路由到哪个 decode 实例，以及到达 decode 实例后应在何时被调入 running batch。
- 现有方法在这两个层面都倾向于采用局部、单指标、短视的决策，只利用当前可观测状态，而缺乏对请求未来输出长度的有效认知。
- 结果是：跨实例层面出现多维负载失衡，实例内层面出现 preemption 与资源闲置并存，两者共同拉低系统端到端 goodput。
- 更重要的是，这两个问题并不是两条割裂的故事，而是共享同一个根因：系统无法在决策时可靠感知请求未来输出长度及其不确定性。
- 本节将从两个 observation 出发，分别建立跨实例路由和实例内调度的动机链，并最终收束为统一根因、核心挑战与总体设计方向。

## 分：Observation 1 —— Prefill-to-Decode 实例间调度

### §2 为什么需要三维负载建模：单一负载视角无法刻画 decode 实例的未来瓶颈

**首句**：要做好 P2D 路由，系统不能只判断“哪个实例现在更忙”，而必须判断“请求落地后会把哪个实例推向什么瓶颈”，这正是建模负载而非只看单一统计量的原因。

**本段内容**：
- 路由决策真正关心的不是实例当前 queue 长不长、batch 大不大或 KV 用量高不高，而是新请求进入后会不会让该实例更快触碰其主导瓶颈，并最终拉低 goodput。
- 只看单一统计量会系统性失真。例如，只看 queue length 或 batchsize 会忽略长上下文带来的 KV 压力；只看 batch tokens 会把“少量长请求”和“大量短请求”混成同一种负载；只看 kv_usage 这一工程 proxy 又无法区分 slowdown 来自总显存容量逼近上限，还是来自并发升高带来的计算与带宽竞争。
- 换言之，P2D 路由需要的不是一个抽象的“忙闲分数”，而是一个能够回答“这个实例为什么忙、接下来会因为什么继续变忙”的状态表示。只有先把负载建模成可分解的瓶颈状态，路由器才有可能从“看到当前负载”走向“估计未来风险”。
- 对 decode 阶段而言，这个状态表示之所以自然地落在三维，而不是一维或任意更多维，是因为单步 decode 的主要资源约束正对应三种不同的物理预算：计算预算、显存带宽预算和总显存容量预算。三者分别回答三个不同问题：当前并发请求数是否已把计算推到 TPOT 边界；当前运行 token 工作集是否已把带宽预算耗尽；当前模型权重、中间激活与 KV cache 的总占用是否已把设备显存逼近上限。
- 更重要的是，这三种压力的驱动因素并不相同。并发请求数 $n_{req}$ 更直接推高计算项；运行 token 总量 $m_{tok}$ 更直接推高 attention 相关访存与带宽项；而容量项在论文建模中由模型权重、中间激活和 KV cache 三者共同决定。也正因为驱动因素不同，同样的 batchsize、同样的 batch tokens 或同样的 kv_usage proxy，都可能对应完全不同的真实瓶颈。
- 基于这一点，本文采用三维负载度量 $L_C$、$L_M$、$L_K$ 近似描述 decode 实例的在线瓶颈状态（对应 modeling.py）。其中，$L_C$ 表示 decode 一步的理论 FLOPs 相对于 TPOT 预算形成的计算压力，$L_M$ 表示 KV cache 工作集与激活工作集相对于单步带宽预算形成的带宽压力，$L_K$ 在论文中的严格定义是总显存占用率，即

$$
L_K = \frac{M_{weights} + M_{act} + M_{kv}}{M_{total}},
$$

- 其中 $M_{weights}$ 表示模型权重占用，$M_{act}$ 表示中间激活占用，$M_{kv}$ 表示 KV cache 占用，$M_{total}$ 表示设备总显存容量。也就是说，论文中的第三维并不是狭义的“KV cache 占用率”，而是包含模型权重、中间激活与 KV cache 在内的总显存容量压力。
- 但在当前工程实现中，出于在线可得性与实现复杂度考虑，我们使用 vLLM 运行时提供的 kv_usage 作为 $L_K$ 的近似代理。这一近似利用了一个工程事实：模型权重在单实例内近似常量，而 decode 阶段最主要、持续增长且最能决定容量风险的部分通常是 KV cache；因此 kv_usage 可以作为总显存占用率的一个可实现 proxy，但它不是论文层面第三维定义本身。
- 瓶颈分数 $L_{\text{bottle}} = \max(L_C, L_M, L_K)$，用于近似刻画当前主导瓶颈。这里需要强调：这一建模当前更应被理解为具有较强物理解释性的在线近似状态，而不是已经被完全验证的唯一正确决策变量；其“是否足以驱动在线决策”仍需由后续模型校验结果进一步支撑。

### §3 单实例的主导瓶颈随时间持续切换 [实验 2]

**首句**：即使在单个 decode 实例上，主导瓶颈也会随请求到达与完成在 compute、memory 和 total-memory-capacity 之间反复切换；其中第三维指的是总显存容量压力，而工程上通常以 kv_usage 近似观测。

**本段内容**：
- 实验设置：1P1D 在线发送请求，定时采集三维指标。
- 观察：batch 增大时 compute 先升；随着 KV 持续累积并带动总显存占用上升，memory 和第三维容量压力追上；请求完成释放后总显存容量压力回落，但 compute 又因新请求进入而再次上升。
- 结论：实例瓶颈是动态切换的，因此任何只看单一指标的路由在某些时间窗口内都不可避免地失真。

### §4 不同工作负载配置下的主导瓶颈维度不同 [实验 3]

**首句**：不同的 input/output 长度、QPS 和 TPOT 配置组合会导致 decode 实例处于完全不同的主导瓶颈维度。

**本段内容**：
- 实验设置：1P1D 离线遍历多种 $(input\_len, output\_len, qps, slo\_tpot)$ 配置，统计每组配置下三维指标各自成为最大值的频率占比。
- 观察：短输入、长输出、高 QPS 更偏向 compute 主导；长输入、长输出更偏向总显存容量压力主导；中间区域则常在三者之间切换。
- 结论：瓶颈切换不仅随时间变化，也随工作负载配置变化，因此路由策略不能假设实例总是被某一个固定维度主导。

### §5 缺乏多维瓶颈感知的路由会导致实例间负载失衡 [实验 1]

**首句**：当 P2D 路由不具备多维瓶颈感知能力时，decode 实例之间会出现系统性的负载失衡。

**本段内容**：
- 实验设置：2P6D，轮询路由在线发送请求，监测 6 个 decode 实例的三维指标。
- 观察：实例间瓶颈分数差异明显，且失衡不只体现在某一维度，而是 compute、memory 以及总显存容量压力这三个维度都会出现偏斜；第三维在工程监测中可由 kv_usage 近似反映，但并不等同于“KV cache usage 本身就是定义”。
- 结论：轮询代表了一类不具备未来瓶颈感知能力的方法；在输出长度未知且方差较大时，这类方法会系统性造成实例间负载不均。

### §6 基于已知输出长度的负载均衡路由可明显提升 goodput [实验 4]

**首句**：如果路由器完全知道每个请求的输出长度并据此实现负载均衡，goodput 相比轮询可观察到明显提升。

**本段内容**：
- 实验设置：1P3D，轮询 vs Oracle 路由。Oracle 假设已知真实输出长度，将请求调度到未来 tokens 最少的实例，同时监测 3 个实例的三维指标。
- 观察：Oracle 路由的 goodput 明显优于轮询，且其三维指标分布更均衡。
- 结论：只要能够更准确地估计请求落地后的未来负载，跨实例负载均衡就可能明显提升系统吞吐；问题在于真实场景下输出长度未知，如何在相同信息边界下逼近这种上界。

### §7 当前设定下，均值预测与 Oracle 路由仍存在明显差距，这提示一阶统计量可能不足 [实验 5]

**首句**：在当前实验设定下，均值预测路由与 Oracle 路由之间仍存在明显差距，这提示仅依赖一阶统计量可能不足以稳定逼近更优策略。

**本段内容**：
- 当前实验设置中，对每条请求生成 50 次取均值模拟点预测器，并按均值做路由；对应 Oracle 路由则使用真实长度信息。
- 观察：均值预测路由的 goodput 仍明显低于 Oracle 路由。
- 这一差距至少说明两点：其一，均值无法刻画单次生成对均值的偏离；其二，LLM 输出长度具有随机性，单次采样可能显著偏离均值，使实例实际承受的负载超出预期。
- 但我们也要强调：由于当前对照仍混入了“信息质量”和“控制策略”两个因素，这一结果更适合作为“分布信息可能必要”的初步证据，而不应在此阶段被表述为最终结论。
- 后续需要在统一终止策略和统一信息边界下重做公平对照，进一步确认差距到底来自点预测本身，还是来自控制变量差异。

### §8 P2D 调度的论证链小结

**首句**：上述实验已经构成了一条从“瓶颈刻画”到“均衡收益”再到“更丰富信息形态可能必要”的基本论证链。

**本段内容**：
1. 瓶颈是什么 [§3 + §4]：decode 实例负载是多维且动态切换的。
2. 现有方法的问题 [§5]：缺乏多维瓶颈感知会导致实例间失衡。
3. 问题值得解决吗 [§6]：已知真实长度的 Oracle 路由能明显提升 goodput。
4. 点预测够不够 [§7]：在当前设定下，均值预测仍明显低于 Oracle，提示一阶统计量可能不足。
5. 设计方向：基于三维负载建模，纳入 running 与 waiting 状态，并引入能够表达风险的输出长度分布预测，逐步逼近更优路由效果。

## 分：Observation 2 —— Decode 实例内调度

### §9 Decode 实例内调度的核心矛盾不是算得快不快，而是何时调入 waiting 请求

**首句**：Decode 实例内调度的核心问题，不是单步 decode 能否执行，而是在 waiting 队列存在时，系统应以多大的并发度接纳新请求进入 running batch。

**本段内容**：
- Decode 阶段中，每个 running 请求都会持续累积 KV cache，并随着生成推进逐步增加总显存占用与带宽压力。
- 调入更多请求可以提升并行度、改善设备利用率；但并发度过高时，请求间会争夺资源，甚至触发 preemption 与抢占传播。
- 因而，实例内调度面对的是一个典型平衡问题：过保守会造成资源闲置，过激进会造成干扰加剧和抢占恶化。
- 这意味着实例内调度的关键决策不是“当前能不能执行一步 decode”，而是“现在是否应让一个 waiting 请求进入 running batch”。

### §10 固定单请求长度时，以 batchsize 为主轴同样刻画了总负载升高下的倒 U 型变化 [实验 A]

**首句**：在固定单请求长度的条件下，batchsize 是实例内调度直接控制的并发变量；而由于此时 batchsize 与 batch_tokens 成正比，沿着 batchsize 观察到的 goodput 先升后降，也等价表明总负载升高时存在最优并发区间。

**本段内容**：
- 实验设置：1P1D，固定每个请求的上下文长度为 $512 + 1024$，以最大速率发送不同 batchsize 的请求。
- 因为单请求长度不变，batchsize 增大时 batch_tokens 同步增大，实例承受的总负载也同步上升。
- 以 batchsize 为横轴更贴近调度决策本身，因为系统真正控制的是同一时刻允许多少个请求进入 running batch。
- 观察：goodput 在小 batchsize 区间随并发提升而上升，但超过某个峰值后开始下降。
- 结论：实例内调度存在最优并发区间。小于该区间是利用不足的代价，大于该区间则是资源干扰与 preemption 风险放大的代价。

### §11 固定 batch_tokens 时，goodput 仍然呈倒 U 型，说明总 token 数不是决定性能的充分条件 [实验 B]

**首句**：即使固定同一时刻实例内的总 token 数，随着 batchsize 增大、单请求 seq_len 减小，goodput 仍先升后降，这说明 batch_tokens 不是决定 decode 性能的充分统计量。

**本段内容**：
- 实验设置：1P1D，将 $batch\_tokens$ 固定为 32000，只改变 batchsize，因此 batchsize 越大，每个请求的 seq_len 越短。
- 如果 decode 性能只由总 token 数决定，那么在 batch_tokens 固定时，goodput 应近似保持不变。
- 但实验结果仍然出现明显倒 U 型，这说明请求粒度本身会改变 decode 实例的运行状态。
- 一方面，更高的 batchsize 在低并发区间可以带来更好的吞吐利用；另一方面，过多的并发请求会放大调度开销、状态竞争和抢占风险。
- 结论：decode 内调度不能只看“现在总共有多少 token”，还必须看“这些 token 是由多少个请求构成的”。

### §12 在相同 batch_tokens 下，input/output 构成会改变最优并发点的位置 [实验 B 细分]

**首句**：在 batch_tokens 相同的情况下，不同的 input/output 长度构成对应不同的最优 batchsize，说明实例内调度必须感知长度结构，尤其是输出长度风险。

**本段内容**：
- 实验设置：在实验 B 的基础上，进一步细分三类长度构成：$(4000, 28000)$、$(16000, 16000)$、$(28000, 4000)$。
- 三组实验保持总 token 数相同，但 goodput 峰值对应的 batchsize 明显不同。
- 观察：output 占比越大，峰值 batchsize 越小；input 占比越大，实例可承受的最优并发度越高。
- 这说明同样的总 token 负载，如果更多 token 是“未来还会持续增长的 output”，则它对后续调度的风险更高；如果更多 token 是静态 input 上下文，则未来代价相对较低。
- 结论：长度总量相同不代表未来代价相同，真正影响实例内调度的，不只是当前 token 占用，还有这些 token 在未来是否会继续增长、增长多久。

### §13 两组实验共同说明：decode 内调度高度依赖长度结构，固定激进或保守策略都不稳健

**首句**：实验 A 和实验 B 共同说明，decode 实例内存在稳定的倒 U 型并发规律，而最优点同时受总负载、请求粒度和 input/output 构成影响，因此固定的激进或保守策略都不稳健。

**本段内容**：
- 实验 A 说明：当调度器提高 batchsize 时，系统并发度与总负载同步上升，decode 内调度存在“利用率提升”与“干扰加剧”之间的平衡点。
- 实验 B 说明：即使总负载不变，这个平衡点也会因请求粒度和长度构成而改变。
- 因此，实例内调度的更合理方向不是固定 batchsize，也不是固定 batch_tokens 阈值，更不是一味多塞请求或一味保守等待。
- 现有证据强烈指向一种长度感知的动态并发控制：根据请求的长度结构和未来输出风险，决定 waiting 请求何时进入 running batch。

### §14 从动机到方法：实例内调度与输出长度信息高度相关，但“决定性作用”仍需 Oracle 对照闭环验证

**首句**：既然最优并发点依赖于请求未来会生成多少 output token，那么实例内调度与输出长度信息高度相关；但长度信息对策略上界的决定性作用，仍需通过 Oracle 对照进一步闭环验证。

**本段内容**：
- 当前 decode 实例可以直接观测到的，主要是 running 请求数、当前上下文长度，以及 kv_usage 这类用于近似第三维总显存容量压力的工程 proxy，外加 waiting 队列长度。
- 但这些量只能描述“现在的状态”，并不能充分描述“把某个 waiting 请求调进来之后未来会造成多大代价”。
- 一个看起来当前长度不长的请求，可能在未来生成很长 output，从而长期推高 KV cache，并进一步抬升其所对应的总显存容量压力，放大后续 preemption 风险。
- 因而，现有证据强烈表明：实例内调度若要稳定逼近更优并发控制，需要利用请求未来输出长度及其不确定性；但“是否必须、强到什么程度”，仍需要 Oracle 对照来完成证据闭环。

### §15 若要补强实例内动机链，最关键的是补一个统一信息边界下的 Oracle 调度对比实验

**首句**：现有两组实验已经足够建立 decode-only 的问题存在性和问题复杂性，而如果还要进一步补强动机链，最关键的不是重复画负载曲线，而是在统一信息边界下补一个 Oracle 调度对比实验。

**本段内容**：
- 现有两组实验已经证明：激进与保守两端都非最优，且最优点依赖请求输出长度结构。
- 下一步最关键的对照是：在统一可见状态集合、统一决策时机和统一终止策略的前提下，比较激进策略、保守策略、Oracle 策略、均值预测策略和分布预测策略。
- 如果 Oracle goodput 明显更高，就能更直接地说明：实例内调度的问题不只是“调度很难”，而是“缺失长度信息限制了当前策略上界”。
- 若再比较均值预测与分布预测，则可进一步确认实例内调度到底需要点信息还是风险分布信息。

### §16 Decode 实例内调度的论证链小结

**首句**：上述 decode 实验已经构成了从“倒 U 型两难”到“长度结构依赖”再到“Oracle 闭环缺口”的完整动机链。

**本段内容**：
1. 两难存在 [§10]：固定配置下 goodput 随 batchsize 呈倒 U 型，说明激进与保守两端均非最优。
2. 总 token 不是充分统计量 [§11]：即使固定 batch_tokens，goodput 仍会明显变化。
3. 最优点依赖长度结构 [§12]：相同 batch_tokens 下，不同 input/output 构成对应不同最优并发点。
4. 设计方向 [§13 + §14]：实例内调度与输出长度风险高度相关，强烈指向长度感知的动态准入控制。
5. 闭环缺口 [§15]：若要把这一方向从“强烈指向”提升为“实证闭环”，Oracle 对照实验是最关键的一步。

## 总结（总）

### §17 两个 observation 收束为两个核心调度问题

**首句**：上述两个 observation 揭示了 PD 分离架构下 goodput 下降的两个来源，对应两个必须同时回答的调度问题。

**本段内容**：
1. P2D 路由问题：prefill 完成后，系统应将请求路由到哪个 decode 实例，才能在多维动态瓶颈下实现整体负载均衡、提高 goodput。
2. 实例内调度问题：在某个 decode 实例内部，系统应何时调入 waiting 请求、以多大并发度运行，才能在 preemption 风险与资源利用率之间动态取得平衡。
3. 两个问题并不独立：错误的路由会改变实例内竞争格局，错误的实例内调度又会放大路由的后果。

### §18 两个问题的统一根因：缺乏对请求未来输出长度的可用认知

**首句**：两个调度问题的表象不同，但共享同一个根因：现有方法缺乏对请求未来输出长度的可靠认知。

**本段内容**：
- 对 waiting 请求，系统只知道 prompt length，却不知道最终会生成多少 token。
- 对 running 请求，系统虽已观察到当前已生成长度，却不知道剩余生成还会持续多久。
- 跨实例路由只能看到“当前负载”，看不到“请求落地后的未来瓶颈”；实例内调度只能看到“当前能不能塞下”，看不到“塞进来后是否会触发抢占传播”。
- 因此，未来输出长度不是附加优化项，而是统一两阶段调度的关键信号。
- 更进一步，P2D 部分当前结果提示点预测可能不足以替代分布信息；对两阶段调度而言，能够表达风险的长度分布是更自然的统一信号接口。

### §19 挑战 1：如何在低系统开销下获得足够有用的分布信息

**首句**：要让预测真正服务在线调度，核心挑战在于如何在不引入明显系统开销的前提下获得足够有用的分布信息。

**本段内容**：
- 预测器过重会抵消调度收益，预测器过轻或只做粗糙点估计又无法支撑细粒度两阶段决策。
- 需要的是一种 practical prediction：它既能部署在真实 serving 路径上，又能稳定输出足以支撑风险感知调度的长度分布。
- 但“可部署”不能只停留在概念上，后续必须通过联合开销评估证明预测与调度带来的净收益在关键负载区间内为正。

### §20 挑战 2：如何验证三维负载模型足以驱动在线决策

**首句**：三维负载模型不仅要有物理解释性，还必须被验证为足以驱动在线调度决策的状态变量。

**本段内容**：
- 当前三维负载建模提供了一个清晰的物理近似，但“是否足够可靠地用于决策”仍需实证校验。
- 为了避免后续只报告趋势、不报告门槛，本文预先声明三类验收标准：其一，以真实主导瓶颈事件为标签时，瓶颈分类任务的 macro-F1 不低于 0.75 且 one-vs-rest AUC 不低于 0.85；其二，在不同 workload 配置下，上述核心指标相对校准配置的下降不超过 10%；其三，在状态输入加入 $\pm 5\%$ 扰动时，使用该状态驱动的在线决策其 goodput 相对下降不超过 3%，preemption rate 上升不超过 5%。
- 也就是说，三维负载模型在本文中不应被视为不证自明的真理，而应被视为一个需要被验证的决策状态表示；只有满足上述验收门槛，才可被进一步视为达到在线部署所需的可决策性。

### §21 挑战 3：如何设计有效且公平的两阶段协同调度算法

**首句**：有了预测信息之后，核心挑战不仅是如何设计跨实例路由与实例内调度算法，还包括如何在统一信息边界下公平地验证这些算法。

**本段内容**：
- 跨实例阶段需要从单维指标走向三维负载建模，并逐步纳入 running、waiting 以及预测输出长度，估计实例未来瓶颈。
- 实例内阶段则需要根据请求状态与预测长度风险，动态控制 waiting 到 running 的调入节奏，在 preemption 风险与资源利用率之间取得平衡。
- 两阶段不能各自为政，而需要共享一致的负载刻画与风险认知。
- 同时，Oracle、均值预测和分布预测之间的比较必须遵守统一的信息可见性协议，否则实验差异就无法被严格归因。

### §22 挑战 4：如何处理预测误差与联合开销带来的系统风险

**首句**：预测误差与控制开销都不是实现细节，而是两阶段调度必须共同面对的核心系统问题。

**本段内容**：
- 预测不足可能低估长尾请求，把它们错误地送入脆弱实例或过早调入 running batch。
- 预测过保守则可能让调度器过度回避某些实例或推迟准入，造成资源闲置。
- 实例内调度对此尤为敏感，因为它直接改变单个请求未来代价的估计，从而改变 preemption 风险与利用率之间的平衡。
- 此外，即使预测方向正确，如果预测和调度开销抵消了吞吐收益，它仍不构成一个有部署价值的系统设计。

### §23 核心思路引出

**首句**：基于以上分析，本文提出一个由输出长度分布预测驱动的两阶段协同调度框架，并将以统一协议、统一指标和补充对照实验验证其必要性与有效性。

**本段内容**：
- 跨实例层面：基于 decode 实例的三维负载状态、running/waiting 队列信息和预测输出长度分布，估计请求落地后的未来瓶颈，做出更稳健的 P2D 路由决策。
- 实例内部：结合请求状态、显存利用率与预测长度风险，动态平衡 waiting 请求的调入节奏，避免激进调度和保守调度两个极端。
- 两个层面共享对 decode 未来瓶颈的建模，共同提升系统在长输出、高方差与突发负载下的端到端 goodput。
- 但与前一版不同，本版动机将明确把 Oracle 闭环、公平对照、指标形式化、模型校验和净收益验证视为后续论证中不可缺少的证据环节，而不再把它们隐含为已被证明的事实。
