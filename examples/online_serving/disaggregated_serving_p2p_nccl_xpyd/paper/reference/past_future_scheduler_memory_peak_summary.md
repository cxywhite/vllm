# Past-Future Scheduler 显存峰值调度策略总结

## 论文信息

- 标题：Past-Future Scheduler for LLM Serving under SLA Guarantees
- 核心问题：在连续批处理的 LLM serving 中，如何在满足 SLA 的前提下，提高 goodput，同时避免保守调度的低利用率和激进调度的频繁 eviction。

---

## 一句话总结

这篇文章的核心思想是：**不要只看当前已经占用的显存，而要预测“如果现在把 waiting 请求加入 running batch，未来某个时间点的峰值显存会不会超出容量”**。为此，它把调度拆成两个步骤：

1. 用最近完成请求的输出长度分布，动态预测当前 running / waiting 请求的最终输出长度。
2. 基于这些预测长度，计算当前 batch 在未来各个时间点的显存占用，并取其中的峰值作为 `future required memory`；只有当这个未来峰值不超过可用显存时，才准入新请求。

因此，它本质上是一个**面向未来显存峰值的准入调度器**，而不是简单的“当前能塞下就塞”或者“按最坏情况预留”。

---

## 1. 论文想解决什么问题

文章把现有 LLM 请求调度器分成两类：

### 保守调度

- 假设每个请求都会生成到 `max_new_tokens`。
- 因而在加入新请求时，按最坏情况预留显存。
- 好处是几乎不会爆显存。
- 问题是显存利用率低，很多请求只能排队，TTFT 容易恶化，goodput 低。

### 激进调度

- 只根据当前输入长度或当前剩余显存决定是否接纳请求。
- 倾向于尽可能早地把 waiting 请求塞进 running batch。
- 好处是当前显存利用率高。
- 问题是它忽略了输出 token 会继续增长，导致未来某个时刻显存峰值超出容量，进而触发 request eviction、requeue 和 recomputation。
- 一旦发生 eviction，MTPOT 和 goodput 会明显恶化，尤其在 decode-heavy 场景更严重。

这篇论文的基本判断是：**当前显存占用不是调度决策的充分依据，真正决定是否安全准入的是“加入该请求后，未来的峰值显存需求”。**

---

## 2. Past-Future Scheduler 的两个核心组件

文章的方法由两个模块组成：

### 2.1 输出长度分布预测

作者没有尝试对每个请求做昂贵的语义级长度预测，而是利用一个更轻量的观察：

- 对很多在线服务来说，**相邻时间窗口内请求的输出长度分布是相似的**。
- 即使全局分布会随时间变化，短时间内的局部分布通常仍然稳定。

基于这个观察，调度器维护最近完成请求的输出长度集合 $L_h$，并构造经验分布：

$$
P(l) = \frac{C(l, L_h)}{|L_h|}
$$

其中 $C(l, L_h)$ 表示历史窗口中输出长度等于 $l$ 的次数。

然后它用这套分布做两件事：

- 对 waiting 请求：直接从 $P(l)$ 中采样一个预测输出长度。
- 对 running 请求：已知该请求已经生成了 $l_t$ 个 token，则从条件分布 $P(l > l_t)$ 中重新采样，动态更新它的最终长度预测。

这一步的关键不是“精确预测某个具体请求”，而是**在线逼近当前服务流量下的输出长度风险分布**。相比语义模型或专门训练的 predictor，这种做法：

- 无额外推理开销
- 模型无关
- 可以在每个 decode step 动态修正 running 请求的剩余长度估计

### 2.2 Future Required Memory 估计

有了每个请求的预测最终长度之后，文章进一步提出：

**判断一个 waiting 请求能否现在加入，不应该看当前显存，而应该看加入之后，当前 running batch 在未来完成全过程中所需的最大显存。**

作者把这个量称为 `future required memory`。

其直觉是：

- 每个请求的显存占用会随着 decode 逐步增长。
- 但不同请求会在不同时间结束，并释放显存。
- 因此，整批请求的显存需求并不是简单地把所有请求总长度直接相加。
- 未来真正危险的时刻，往往发生在某些请求即将结束或刚结束前后的几个时间点。

论文的做法是：

1. 根据每个请求“预测剩余生成长度”对 running batch 排序。
2. 枚举“某个请求完成时”的未来时间点。
3. 对每个这样的时间点，计算 batch 当时需要的显存。
4. 取这些未来时间点中的最大值，记为 $M^*$。

也就是说：

$$
M^* = \max_t M_t
$$

这里的 $M_t$ 不是当前显存，而是**把一个 waiting 请求现在准入后，未来某个关键时刻的显存占用**。

调度决策就变成：

- 若 $M^*$ 不超过系统可用显存，则现在准入。
- 若 $M^*$ 会超过容量，则先不准入，等几个 decode step 之后再重新评估。

这就是文章所谓的 “Past-Future” 含义：

- `Past`：利用最近历史请求的输出长度分布。
- `Future`：估计加入请求后未来的峰值显存需求。

---

## 3. 这个调度策略和激进 / 保守方法到底差在哪

文章用一个非常清楚的例子说明三者差异：

### 保守调度

- 只要最坏情况下所有请求总显存还放不下，就一直不接纳新请求。
- 结果是要等到更晚的时间点才放新请求进来。
- 代价是队列等待更长，显存利用率偏低。

### 激进调度

- 看到“当前还能塞下”就立刻把请求加入。
- 但随着 running batch 继续生成输出，未来峰值显存可能超过容量。
- 一旦超限，就需要 eviction，请求被赶出去后重新排队甚至重算。
- 这会直接伤害 MTPOT 和 goodput。

### Past-Future 调度

- 它既不按最坏情况静态保守预留，也不只看当前占用。
- 它会判断：**如果现在加入，会不会在未来某个时间点爆显存；如果会，那么最早在什么时候加入才安全。**
- 因而它常常不是“立刻加”，也不是“等很久再加”，而是“等几个 step，在恰当时间点加入”。

所以它本质上是一种**显存峰值感知的延迟准入策略**。

---

## 4. 这篇文章中的“显存峰值调度策略”可以如何概括

如果只提炼它的调度逻辑，可以压缩成下面四步：

1. 收集最近一段时间已完成请求的输出长度，构造历史输出长度分布。
2. 对 waiting 请求预测最终输出长度；对 running 请求根据已生成长度动态更新剩余长度预测。
3. 假设把当前 waiting 请求加入 running batch，计算未来各关键时间点的显存占用，并得到未来峰值显存 $M^*$。
4. 仅当 $M^*$ 不超过可用显存时才准入，否则延迟到后续 step 再判断。

因此，这不是传统的 batch-size 控制，也不是简单的 watermark 控制，而是：

**一个以未来峰值显存为约束、以长度分布预测为支撑的在线 admission control。**

---

## 5. 它为什么有效

论文给出的核心原因有两个：

### 5.1 它比保守调度更不浪费

保守调度假设每个请求都可能生成到上限，这在真实流量中通常过于悲观。Past-Future 利用历史分布得到更接近真实的输出长度估计，因此能够在不显著增加风险的前提下更早准入更多请求，提高显存利用率。

### 5.2 它比激进调度更少触发 eviction

激进调度只看到“现在还能放下”，但 Past-Future 看到的是“未来峰值是否会超出容量”。因此它能避免很多“当前能进、未来爆掉”的错误准入，尤其在 output 较长、decode-heavy 的工作负载下更明显。

---

## 6. 论文中的结果结论

从实验上看，文章主要得出以下结论：

- 在高负载下，Past-Future 的 goodput 明显优于保守和激进调度，论文摘要中给出的量级是最高可达 2 到 3 倍。
- 在 prefill-heavy 场景中，激进调度和 Past-Future 都可能表现不错，因为输出增长较短，未来显存风险相对小。
- 在 decode-heavy 场景中，激进调度容易因为忽略未来输出显存而频繁 eviction，goodput 会先升后降；Past-Future 则更稳定。
- Past-Future 的调度开销很低，作者报告其调度计算开销低于模型推理时间的 1%。
- 单纯通过调 watermark 或 overcommit 参数，无法同时解决“高利用率”和“低 eviction”这两个目标；Past-Future 的优势来自它对未来负载的显式建模，而不是参数调优。

---

## 7. 这个方法的关键假设与局限

这篇文章的方法非常实用，但它依赖几个重要假设：

### 7.1 核心状态维度主要是显存

它的建模核心几乎完全围绕 KV cache / memory capacity 展开，默认调度瓶颈主要来自显存峰值，而不是计算或带宽。

### 7.2 输出长度预测依赖局部平稳性

它假设相邻时间窗口的输出长度分布相似。如果服务流量分布突变很剧烈，这种基于最近历史窗口的经验分布可能会滞后。

### 7.3 预测是群体分布级，而不是请求语义级

它没有利用请求内容本身来判断该请求会不会特别长，而是通过全局历史分布加运行时已生成长度去修正。好处是轻量；代价是个体差异感知较弱。

### 7.4 它解决的是单实例内 admission 问题

它主要回答的是“一个 waiting 请求现在应不应该进这个 running batch”，而不是多实例之间如何路由。

---

## 8. 对我们后续讨论 decode 实例内调度的直接启发

这篇文章和我们要讨论的问题高度相关，直接启发有三点：

### 8.1 它提供了一个非常清晰的基线问题定义

实例内调度的核心可以明确写成：

**对一个 waiting 请求，现在是否应该让它进入 running batch？**

Past-Future 给出的回答方式是：比较“现在准入后未来峰值显存是否可承受”。

### 8.2 它证明了“长度信息”对实例内调度确实有决策价值

它不是泛泛地说长度预测有用，而是把长度预测直接接到了 admission control 上：

- 没有长度信息时，只能在激进和保守之间拍脑袋调参数。
- 有长度信息后，可以把问题变成面向未来风险的准入判断。

这对我们后续设计 decode 实例内调度器很重要，因为它给出了“预测如何进入系统决策”的具体接口。

### 8.3 它的不足也正好对应我们可以继续扩展的方向

如果我们的系统观察表明 decode 实例不仅受显存约束，还受计算和显存带宽约束，那么 Past-Future 的一维显存峰值建模就不够了。换句话说，它提供的是一个很强的起点，但不是最终答案。后续可以继续扩展为：

- 从一维显存风险扩展到多维未来负载风险。
- 从历史经验分布扩展到更强的 per-request 输出长度预测。
- 从单实例 admission 扩展到和 P2D 路由协同的两阶段调度。

---

## 9. 最简摘要

Past-Future Scheduler 的显存峰值调度策略，本质上是：**利用最近历史请求的输出长度分布，动态预测 running / waiting 请求的最终输出长度；然后估计“如果现在准入该请求，未来完成整个 running batch 过程中所需的最大显存”是否超过容量；只有未来峰值安全时才允许准入。** 这使它能够在保守调度的低利用率与激进调度的高 eviction 之间找到更合理的中间点，尤其适合 decode-heavy 的 LLM serving 场景。
