# GWF vs KV-threshold 实验报告

生成：2026-11-15。口径：goodput = "Output token goodput (tok/s)"，SLO = TTFT≤1000ms ∧ TPOT≤30ms。

---

## 1. 实验目标

回应审稿人 Observation 2 的论断——"大多数系统通过跟踪 KV cache 使用率并保留 buffer 来做准入，而不是无视 cache 利用率地放请求"。

本实验直接对比两种实例内准入策略：

- **GWF**：我们的预测式准入调度（基于输出长度预测决定准入，带反饥饿机制）；
- **KV-threshold**：审稿人描述的朴素做法——跟踪实际 KV 使用率、到阈值就停止准入、保留 buffer。

问题：在长尾负载 kv1p6 上，预测式准入（GWF）是否比朴素 keep-a-buffer（KV-threshold）更好？

---

## 2. 实验配置

### 2.1 公共配置（两臂一致）

| 项 | 值 |
|---|---|
| 模型 | Qwen-2.5-7b-Instruct |
| 硬件 | A800-SXM4-80GB × 8，PD 4:4 |
| gmu | 0.8 / 0.8（固定约束）|
| SLO | TTFT≤1000ms ∧ TPOT≤30ms；goodput = Output token goodput (tok/s) |
| 路由 | scheme4 预测路由（真实 BERT 预测）|
| trace | `qwen_o2000_kv1p6`：4080 条，output p50=688 / p90=11209 / max=13305（长尾）|
| 请求数 | 4080 |

### 2.2 KV-threshold（审稿人描述的 keep-a-buffer）

跟踪实际 KV cache 使用率，当使用率达到 **80%** 时停止从等待队列准入新请求（保留 20% buffer），低于阈值恢复准入。预测无关、无模拟、无自定义抢占。

### 2.3 GWF（我们的预测式准入）

基于输出长度预测的准入控制：按预测长度决定是否准入，并带反饥饿的强制准入机制，避免长请求阻塞队列。

（两臂只在"实例内准入策略"不同，路由、trace、SLO、硬件完全一致。）

## 3. 实验结果

| 指标 | GWF | KV-threshold | GWF 优势 |
|---|---|---|---|
| **Output goodput (tok/s)** | **118.80** | 90.56 | **+31%** |
| 成功请求 | 4080/4080 | 4080/4080 | 平 |
| Median TTFT | 618 ms | 482 ms | KV 更低 |
| Mean TTFT | 32.7 s | 68.5 s | GWF 好 2× |
| Median TPOT | 110.30 ms | 120.50 ms | GWF 更低 |
| 吞吐 (tok/s) | 4647 | 3535 | +31% |
| SLO 达标请求数 | 523 (12.8%) | 527 (12.9%) | 打平 |
| SLO 输出 token | 313533 | 314206 | 打平 |
| 墙钟时间 | 2638 s | 3468 s | GWF 快 31% |

**关键数据点**：两者 SLO 达标数打平（523 vs 527，KV 甚至略多），但 KV-threshold 花了 31% 更长的时间（3468s vs 2638s）跑完同样的 trace，因此 goodput（速率）低 31%。

---

## 4. 实验分析

### 4.1 goodput 差距的拆解

```
goodput = SLO 输出 token ÷ 墙钟时间

GWF / KV-threshold = (313533 / 314206) ÷ (2638 / 3468)
                   = 0.998 ÷ 0.761
                   = 1.31
```

**差距 100% 来自"时间"（KV-threshold 慢 31.5%），SLO 达标 token 两者打平（甚至 KV 略多 0.2%）。**

### 4.2 KV-threshold 为什么慢：固定阈值准入被长请求队头阻塞

运行时观测（`[WT][KVBUF]`）：

```
kv_usage=97~99%  running=186~192  waiting=84~95  gated=True
```

- 阈值准入在 KV 达到 80% 后停止准入，但**控制不了已在 running 的请求继续生成 output 把 KV 撑到 99%**；
- 20% 的 buffer 被长尾请求的输出增长吃光，KV 顶满；
- 由于**没有强制准入机制打破队头阻塞**，等待队列积压（84–95），长请求串行阻塞，整个 4080 条 trace 被拖长到 3468s；
- 并发只有 ~190 个长请求在跑（对比 GWF 峰值 266），吞吐掉到 3535（−24%）。

### 4.3 结论

1. **GWF 比 KV-threshold 高 31%**，且差距完全来自吞吐/时间，不是达标质量（两者 SLO 达标数打平）。
2. **朴素 keep-a-buffer 的失败模式是"吞吐坍缩"而非"请求失败"**：KV-threshold 4080/4080 全成功，但固定阈值准入没有反饥饿机制，长尾请求把 buffer 吃光后队头阻塞、跑慢 31%。
3. 这印证了：**"跟踪 KV 使用率 + 保留固定 buffer"不足以应对输出长度不确定的长尾负载**——真正需要的是能预判输出增长、并有反饥饿机制的预测式准入。
